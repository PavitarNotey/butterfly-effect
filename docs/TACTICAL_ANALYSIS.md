# Tactical intelligence and evidence visualization

The existing canonical replay is analyzed by Python and presented in the stadium using the existing replay clock. All three synthetic scenarios use the same engine. The geometry and replay engine contain no runtime player AI, probability model, counterfactual, LLM or physics engine. Geometry does not establish intent, communication, awareness or causal necessity. [Phase 4](PHASE_4_AI_INTELLIGENCE.md) adds a separate Foundry narrative layer over these unchanged measurements; older no-AI milestone limitations below describe the earlier implementation.

The Python definitions and API contract below remain current; earlier timings, test counts and screenshots are historical milestone results. The **Phase 3C/3C.1 frontend experience** now leads with a plain-English finding and a bounded guided replay; manual moment and overlay controls remain available for deeper inspection. See [the experience report](PHASE_3C_EXPERIENCE.md) for presentation behavior and historical validation.

## Run and demo

Use the two server commands in the root README. The backend registry loads the canonical JSON files directly from `frontend/src/replay/`; this repository layout is required for local development.

1. Open http://localhost:5173 and choose **Analyze this moment** below the replay. The main finding explains the active moment; **How we measured this** retains exact evidence and limitations.
2. Choose **Show me in the replay** for the main finding, or **Watch this** on a supporting insight. The validated evidence ID selects a padded interval, relevant actors, one matching overlay and a camera; the shared canonical clock plays it at 1× or an explicitly shown 0.5×. The replay scrolls into view and a caption names the evidence.
3. Use **Replay again**, **Pause/Resume**, **Back to analysis** or close in the caption. Closing/back restores the prior paused timestamp, camera, selection, speed and overlay settings. Manual scrubbing, camera/speed changes, tactical panning or selecting another player interrupt the guide at its current time, restore prior overlay/speed settings and pause. Scenario changes clear the guide.
4. For manual inspection, use the **six moments in The Invisible Run** **seven in The Missed Chance**, or **seven in The Pass That Wasn't Touched**, including the compact **Analytical moment** selector beside the picture. Moment selection pauses and seeks the authoritative clock while preserving the camera. Start with **The initial shape**, **Rowan’s diagonal run** and **Defensive reshaping**; enable **Defensive movement** and **Player relationships**. Amber arrows show recorded displacement, and team-colored tactical rings identify the moment’s actors. The separately selected player has a lime inspection ring.
5. Choose **The passing corridor**. The fixed recorded path is classified using the entire 4.4–5.6 s interval, including moving defenders. Its closest simultaneous defender-to-ball gap is approximately 2.04 m under the default configuration.
6. Enable **Space & coverage** and select **Voss receives**. The blue boundary is a six-metre measurement region around the recorded receiving point, not a heatmap or an assertion that space is undefended. Nearby defensive cover remains visible in the measurements. Choose **The finish** to inspect the recorded shot path and recovery-clearance observation.
7. Scrub backwards or change cameras during manual analysis; annotations follow replay time. Use **Return to replay** or the HUD exit control to hide tactical layers without changing the clock or camera.

Measurements appear in a concise primary finding and expandable supporting evidence. Authored interpretations are labeled separately. Details include units, definitions, stable IDs, assumptions and source event references.

## Architecture and contracts

- `backend/tactics/models.py`: version-1 Pydantic scenario and response contracts. Finite coordinates, complete increasing tracks, team directions, roster/event/possession references, bounds and unknown fields are validated.
- `engine.py`: reusable interpolation, pairwise relationships, speed/displacement, coverage and corridor geometry. These functions accept any valid `Scenario`, independent of showcase player names.
- `service.py`: a registry pointing to all three canonical JSONs, separate authored guides in `guides.py`, computed observations, temporal links and cached overlay samples. The guide supplies player/event references and interpretations; it supplies no alternative coordinates or analytical outcomes.
- `routes.py`: typed read-only FastAPI endpoints.
- `frontend/src/api/schema.d.ts`: generated by the existing OpenAPI workflow. Replay and tactical interfaces are aliases of these generated contracts.
- `frontend/src/tactics/`: API boundary and source verification, UI state, presentation, compact HUD and render-only overlays. The replay clock remains in its existing store.

The scenario teams now declare `attackDirection` (+1 or -1 along X). No player or ball trajectories were changed for this milestone. Player positions are metres in right-handed X/Y/Z coordinates, with Y vertical, yaw 0 facing +Z and π/2 facing +X. The pitch remains 105 × 68 m.

The API evidence contains the SHA-256 of the canonical JSON text. The browser checks that against the exact raw JSON of the active replay fixture before accepting evidence. Mismatches fail explicitly rather than displaying stale analysis over a different play. Replay remains usable when evidence is unavailable. Fetches time out and offer retry; there is no fabricated fallback evidence.

The frontend acceptance boundary also validates nested player/event/evidence/moment references, finite geometry and measurements, path intervals/endpoints, and consistent relationship identity/order between frames before storing a bundle. Proposed static corridors retain two distinct spatial endpoints at the same timestamp. Malformed bundles use the existing unavailable/retry flow; these checks do not recompute Python geometry or classifications.

Plain-English moment copy is scoped to explicit scenario and moment IDs. The three showcases retain their authored wording and qualifications. Unknown scenarios or moments use their supplied title/interpretation with a neutral qualification, rather than selecting another showcase's story from a goal/miss outcome.

## Mathematical definitions

All analytical distances use the X/Z pitch plane. Ball height is retained for visualization and ground-pass validation.

### Sampling and movement

Positions are piecewise linear between timestamped keys. Heading follows the shortest signed angular difference using `atan2(sin Δ, cos Δ)`. Sampling clamps to the track boundaries; interval/query APIs reject invalid times. At an interior key, speed uses the next segment; at the endpoint it is zero, matching the frontend.

Displacement is `p(end) - p(start)`. Longitudinal and lateral displacement are its signed X and Z components. Path length sums planar segment lengths, including partial boundary segments. Mean speed is path length divided by elapsed time; a zero-duration interval has zero mean speed. Instantaneous segment speed is segment length divided by its duration.

Pairwise distance is Euclidean planar distance. A defender is longitudinally goal-side of an attacker when `(defender.x - attacker.x) * attacking_team.attackDirection > 0`. This definition does not imply lateral coverage, awareness or a marking assignment. Team separation reports centroid distance and nearest opposing-player separation. For each player, the API’s `nearestDefender` fields mean the nearest opposing-team tracking centre.

### Passing corridor

A recorded ground-pass analysis uses the actual ball polyline from release to arrival. Ball endpoints must lie within 1.5 m of the passer at release and receiver at arrival. Height must remain at or below 0.5 m. Zero-length paths and nonpositive travel intervals are rejected explicitly. Stationary defenders and duplicate-position segments are valid.

Three different distances are reported:

1. **Static release clearance:** the minimum distance from a defender’s release-time position to any segment of the complete recorded ball-path polyline.
2. **Swept corridor clearance:** the minimum distance between any defender-path segment during travel and any ball-path segment, without requiring simultaneous arrival. Segment intersections yield zero.
3. **Moving ball clearance:** exact simultaneous closest approach between each defender and the ball during travel. Split at the union of their authored timestamps. On each shared linear interval, relative position is `r(u) = r0 + u v`. Its minimizer is `u = clamp(-dot(r0,v)/dot(v,v), 0, 1)`; constant relative positions use u=0. Compare all intervals and defenders, with stable ID/time tie-breaking.

Defaults: corridor half-width **0.9 m**, contested margin **0.6 m**. These are explicit centre-distance thresholds, not calibrated football reach models:

- **Obstructed:** simultaneous moving clearance ≤ half-width.
- **Contested:** moving clearance ≤ half-width + margin, or a defender’s swept path crosses the corridor within its half-width.
- **Clear:** neither condition holds, under this configuration.

A defender can be outside the lane at release yet meet the ball during flight. Conversely, crossing a corridor at another time is conservatively contested even when simultaneous clearance is larger. None of these labels estimates successful-completion probability.

Before release, live overlays show a proposed static corridor from the recorded ball position to the fixed receiving location. It is explicitly labeled static; its color is not a travel-time safety result. At and after release, the observed pass overlay and classification represent the full recorded 4.4–5.6 s goal-scenario travel interval. The primary static-comparison observations use passer-centre-to-receiving-point segments, with that definition attached to the metric. The finish uses the observed shot trajectory rather than a ground-pass classification.

### Available space and recovery

At a fixed receiving point, report nearest-defender distance and the count of defending tracking centres within radius **6 m**, including the boundary. Changes compare that point at two stated timestamps. A larger nearest distance is one geometric change, not proof that an area is unmarked. The density/count may increase as other cover arrives; the UI does not conceal that.

The finish reports simultaneous planar closest approach to the ball for the guide’s recovering players over the shot-to-final-event interval (goal or miss). This is not a reach or save model and ignores the physical extent of bodies and limbs.

## Evidence, interpretations and movement chains

Each observation has a stable ID scoped by scenario/version/moment/player or finding, a category, interval, involved players, event references, metrics with units and definitions, and limitations. A response also carries its source hash and threshold configuration: IDs identify the same semantic observation while values can change with source or thresholds.

Moment interpretations are stored in separate fields with status `authored_interpretation`. Chain edges are explicitly `precedes_not_proven_cause`, with supporting evidence IDs. They express temporal development and a plausible tactical contribution; they do not show what would happen without the run.

The original six moments and new seven moments derive their timestamps from each scenario’s events. The second guide adds a recovery interval and ends at the miss event. They cover initial shape, run, reshaping, pass, reception and finish. All guide references are validated before analysis.

## API

- `GET /health`: unchanged.
- `GET /api/scenarios`: scenario summaries, teams, duration, terminal outcome and source hash.
- `GET /api/scenarios/{id}`: validated version-1 canonical scenario.
- `GET /api/scenarios/{id}/evidence`: observations, authored moments, temporal chain, overlay frames, actual-pass result, shot path, thresholds and limitations. Optional `corridor_half_width`, `contested_margin`, `coverage_radius` query settings are validated and included in output.
- `GET /api/scenarios/{id}/moments`: annotated moment records.
- `GET /api/scenarios/{id}/analysis?t=4.4&start=1&end=4.4`: spatial snapshot and all-player movements over the requested interval. Optional `receiver_id=a9` adds coverage around that player at t. Add `passer_id=a8&receiver_id=a9&pass_start=4.4&pass_end=5.6` for the recorded ground-pass calculation. `corridor_half_width` is configurable here.

Unknown scenarios return 404. Invalid times, references, incomplete pass requests, malformed geometry and thresholds return 422 with useful details. Interactive API documentation is at http://127.0.0.1:8000/docs.

## Synchronization, performance and lifecycle

The existing frame-clock sample drives all tactical geometry. No tactical clock or pairwise per-frame engine runs in JavaScript. Overlay coordinates interpolate Python-produced frames at the union of **all player/ball position keys plus a 0.25 s grid**. Coordinates therefore preserve the replay’s piecewise linear geometry. Metrics and discrete classifications use the most recent measured frame, whose timestamp is displayed; they are not interpolated into invented values. Live highlights and nearest-defender connectors use the same canonical player tracks for exact attachment.

Movement vectors start at the selected evidence interval’s initial position and end at the current position clipped to that interval. The revised goal reshaping vectors include 1–4.4 s, so displacement is already visible when seeking to 2.8 s. The original goal fixture used 3–9 s and a 6 s shift marker. During a guided sequence, only the evidence-relevant paths/links and one matching layer are shown, with highlights on its actors. These are displacement arrows, distinct from selected-player historical trails. Relationships show at most two connectors to avoid crowding. The space disk is a measurement boundary, not a generated heatmap.

Shared meshes and preallocated geometries update in place. The tactical scene is mounted once, hidden when disabled, and its owned geometries/materials are disposed on unmount. Enabling/disabling **manual tactical overlays** does not recreate the canvas or change the replay clock/camera. Starting a **guided replay** intentionally seeks, plays and selects a camera using the existing replay store; it does not create a second timeline.

The original goal showcase bundle measured roughly 190 kB uncompressed and built in about 21 ms locally (single development measurement, not a cross-machine benchmark). Eight source-text/configuration combinations are cached in memory. No database or additional package dependency was added.

## Extend and verify

To add a scenario, author one version-1 JSON, declare attack directions, validate it, register its path in `service.REGISTRY`, and provide a separate authored presentation guide referencing its event/player IDs. Engine functions and the timestamp-analysis API require no football-name-specific changes. Also register the exact raw JSON in the frontend loading boundary. The UI selects either showcase without duplicating the clock, scene or evidence calculations.

To add a finding, implement and test a pure Python calculation with independently calculable fixtures, define structured metrics and limitations, reference source events, add it to the guide’s observations, and map any visualization to actual coordinates. Regenerate OpenAPI and frontend types after contract changes:

```sh
cd backend
uv run python export_openapi.py
cd ../frontend
pnpm generate:api
```

Checks:

```sh
cd backend
uv run pytest
uv run ruff check .
cd ../frontend
pnpm typecheck
pnpm lint
pnpm test
pnpm test:e2e
pnpm build
```

Python and Vitest share `interpolation-parity.json`, an independently specified boundary/midpoint/wrapped-heading fixture. Backend tests also use small scenarios to prove moving interception, non-simultaneous crossings, threshold boundaries, zero paths, overlapping positions, invalid inputs, distance/displacement/coverage and deterministic output/reference integrity. Browser tests exercise actual layer controls, moment seeking, backwards scrubbing, camera/POV stability, speed, mode exit/re-entry, API failure/retry, source mismatch and mobile layout. Tactical screenshots are written to `output/playwright/tactics/` and inspected visually.

Remaining limits: no **measured or calibrated** human reaction/reach/save model, calibrated probabilities, observed visibility/awareness, counterfactual simulation, physics or AI explanations. Phase 3C adds illustrative simulated gaze and goalkeeper/defender/outcome poses, but these are not evidence of attention, contact, a save or intent. Metrics use a visible sample timestamp; threshold changes in the live preview are quantized to at most 0.25 s. The large lazy-loaded Three.js bundle still produces a nonblocking build-size warning. Mobile/browser validation uses local Chromium, not physical-device performance benchmarking.

## Multi-scenario evidence (3A)

`guides.py` contains only authored event/player selections, pressure/cover/balance roles, moment interpretations and presentation focus. It supplies no coordinates or claimed measurement values. `build_bundle()` validates references and uses the same movement, relationship, coverage and corridor functions for all three scenarios. `actualPass` remains the actual ground pass; `shotPath` ends at the guide's terminal event, with no fictitious goal. Evidence IDs are scenario-scoped and source-text/configuration caching remains bounded to eight entries.

`TacticalMoment.focus` chooses corridor, space, relationships or finish presentation. The UI/overlays no longer depend on moment ID names for those choices. Cover evidence includes start/end separation and its change. For the missed chance, the recovery observation is 3.61 → 2.06 m over 12–15 s. These facts are computed, separate from the authored interpretation.

Scenario changes clear all old bundles and hide overlays immediately. Abort plus scenario/attempt/ignore guards prevent late responses from repopulating them. A source hash is computed from identical UTF-8 raw fixture text on both sides; serializing parsed JSON is deliberately avoided. Replay remains available on evidence error, with timeout/retry.

The geometry engine also measures genuine SkillCorner observations through the offline tracking diagnostic command. That data is a separate validated tracking IR with missing observations/provenance; it is not silently converted into complete synthetic tracks. See [FOOTBALL_REALISM.md](FOOTBALL_REALISM.md).


## Phase 3C evidence experience

The default analysis leads with plain-English findings and a guided replay. **Show me in the replay** starts the lead evidence; **Watch this** starts a supporting observation. Each action resolves validated evidence and its owning moment, isolates the appropriate visual layer, highlights relevant players and plays the shared canonical clock through a bounded interval. A caption supplies context and replay/pause/back/close controls. Technical observations, exact metric values, units, definitions, classifications, assumptions, evidence IDs and source hash remain under **How we measured this**. No Python metrics or contracts changed. See [the Phase 3C report](PHASE_3C_EXPERIENCE.md).

A tactical guided replay supplies a temporary camera-framing override, so the overhead **Follow play** button is visible. Choosing it is an intentional manual camera action: it interrupts the guide at the current timestamp, restores the prior analytical layers and playback speed, pauses, and clears the override to resume automatic tactical framing. The guided caption and evidence-specific highlights then disappear.
